# Архитектура — Станция техобслуживания

## Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Backend | **Python 3.12 + FastAPI** | Один из предпочтительных языков по условию задания. Async из коробки, нативная поддержка SSE/WebSocket, отличная поддержка AI-инструментами при разработке (много обучающих данных), быстрый старт без лишнего каркаса. |
| Frontend | **React + TypeScript + Vite** | Один из требуемых фреймворков. TypeScript снижает число тихих runtime-ошибок в статусной машине заявки — это прямо влияет на "доказуемость". Vite — быстрый локальный старт. |
| БД | **PostgreSQL** | Явно предпочтительный вариант по условию. Транзакции и `SELECT ... FOR UPDATE` — то, на чём держится конкурентно-безопасное бронирование слотов (A4/A10). |
| ORM/миграции | **SQLAlchemy (async) + Alembic** | Стандарт для FastAPI, явные миграции нужны, чтобы схема БД была воспроизводима при локальном разворачивании (требование "предварительные требования описаны"). |
| Realtime | **SSE (Server-Sent Events)** | Все realtime-требования задания — это push от сервера клиенту (статус заявки, занятость постов, прогресс робота), обратный канал не нужен. SSE проще WebSocket (нет двусторонней ротации соединения, тривиальный reconnect браузером из коробки) — meньше кода при том же результате. Проверено отдельно (2026-09-12): ни один из запланированных будущих шагов (B/C-грейды, включая AUTONEX C7–C13) не требует, чтобы клиент вёл непрерывный поток данных на сервер по тому же соединению — только редкие дискретные действия (клик "подтвердить", отправка оценки), которые и так идут обычным REST. WebSocket не понадобится, пока не появится принципиально другая фича вроде живого чата с мастером — сейчас такой нет ни в одном плане. |
| Шина realtime-событий | **In-process pub/sub** (`app/services/events.py`): `asyncio.Queue` на подписчика, множество подписчиков в памяти одного процесса | Тот же принцип, что и с APScheduler — один процесс, локальный быстрый запуск важнее масштабируемости, которая тут не нужна. **Известное ограничение:** это работает только в пределах одного процесса — при запуске нескольких воркеров/инстансов backend'а у каждого будет своя изолированная шина, и клиент на одном воркере не увидит событие, опубликованное другим (REST API при этом не ломается, ломается только realtime-обновление между вкладками на разных воркерах). **Путь снятия ограничения:** заменить внутреннюю реализацию `events.py` на `LISTEN`/`NOTIFY` в уже обязательном по стеку PostgreSQL (или на Redis, если он появится в проекте по другой причине) — без изменений в вызывающем коде (`create_booking`, `update_booking_status`, сам `/events`), т.к. модуль спроектирован с узким публичным интерфейсом (`publish()`/`subscribe()`), не завязанным на конкретную реализацию. |
| Фоновые задачи | **APScheduler (in-process)** | Нужны периодические проверки (проактивное ТО, сезонное напоминание по шинам, авто-выполнение задач роботом). Внешняя очередь (Celery+Redis) была бы избыточна и замедлила бы локальный запуск — требование "проект быстро разворачивается локально". |
| Email | **Заглушка** (запись в таблицу `outbox_emails` + лог в консоль) | Разрешено эмулировать внешние сервисы условием задания. |
| ИИ-модуль (C4) | **Pluggable-интерфейс**: реальный вызов LLM API, если задан ключ в `.env`; иначе — rule-based генератор с тем же контрактом | Проект должен разворачиваться локально без секретов; при этом при наличии ключа демонстрируется реальная агентная фича. |
| Авторизация | Клиент — без пароля (идентификация по email при записи). Станция/мастер — один фиксированный логин+пароль из `.env` | Условие явно разрешает "можно обойтись без входа"; полноценная ролевая система избыточна для скоупа задания. |
| Тестирование/доказуемость | **pytest** (unit + async интеграционные тесты) + отдельный скрипт `scripts/prove_concurrency.py` (параллельные запросы через `httpx.AsyncClient` / `asyncio.gather`) | Позволяет буквально показать в терминале, что гонки обрабатываются корректно — то, что просит пункт "доказуемость". |
| Контейнеризация | **docker-compose**: `db` (postgres), `backend`, `frontend`, плюс `db_test`/`backend_test` (профиль `test`) для изолированного прогона тестов | Один `docker-compose up` — весь требуемый "быстрый локальный запуск". Тесты — отдельно, `docker compose --profile test run --rm backend_test pytest`, чтобы не трогать данные живой станции (см. "Бизнес-правила" ниже). |

## Модель данных (актуально, 2026-09-15)

- **Client** (id, email [нормализован в нижний регистр], name)
- **Car** (id, client_id, make, model, mileage, last_service_date, mileage_at_last_service) — последнее поле фиксируется автоматически при выдаче заявки (B5), основа для расчёта "пробег с последнего ТО"
- **Service** (id, name, duration_minutes, price, protected) — каталог услуг; `protected` (п.47, 2026-09-16) — запрещает переименование/удаление через `catalog.py`, стоит у двух сидированных миграцией услуг-"проводников" к хранению шин
- **Post** (id, name) — 3 поста, засеяны миграцией, не управляются через CRUD (фиксированная физическая конфигурация станции)
- **ParkingSpot** (id, name) — 6 мест ожидания (C7, 2026-09-17), тот же принцип, что и `Post` — фиксированная физическая конфигурация, засеяна миграцией, занятость не хранится отдельным флагом, а всегда выводится из живых заявок, ссылающихся на место
- **StationSettings** (id=1, parking_overdue_rate_per_minute) — единственная редактируемая настройка станции сейчас (см. "Бизнес-правила")
- **Booking** (id, client_id, car_id, post_id, start_at, end_at, status, service_ends_at, reminder_sent, tire_offer_declined, parking_spot_id, parked_at, parking_wait_minutes, created_at) — статусы: `accepted / on_post / awaiting_approval / ready / issued / cancelled`. `end_at` — то, что проверяют все EXCLUDE-ограничения занятости; `service_ends_at` — таймер автотаймера (C2), обновляется отдельно и синхронизируется в `end_at` только расширяя (см. "Бизнес-правила" ниже); `tire_offer_declined` (п.47) — клиент отказался от предложения сдать шины на хранение в рамках ЭТОГО визита на "Сезонная замена шин"; `parking_spot_id`/`parked_at`/`parking_wait_minutes` (C7, 2026-09-17) — место ожидания и точка отсчёта ТЕКУЩЕЙ паузы на парковке (до первого приёма, между раундами или после готовности — все переиспользуют одно и то же поле, как посты между заявками), `parking_wait_minutes` копит длительность уже ЗАВЕРШЁННЫХ пауз, прежде чем `parked_at` перезапишется под следующую (см. "Бизнес-правила")
- **BookingService** (booking_id, service_id) — услуги, выбранные в заявке
- **AdditionalWork** (id, booking_id, description, price, duration_minutes, execution_started, service_id, scheduled_booking_id, proposed_by [`mechanic`/`ai`], ai_confidence, ai_reason, status [`pending/approved/declined`]) — `service_id`/`scheduled_booking_id` добавлены для "отдельного визита", когда сразу нет места (см. "Бизнес-правила"); `ai_confidence`/`ai_reason` (C5, 2026-09-16) заполняются только при `proposed_by=ai`, видны ТОЛЬКО станции (оверсайт) — никогда клиенту, см. "Бизнес-правила"
- **TireSet** (id, client_id, car_id, stored_at, issued_at) — хранение шин, "один активный комплект = одна машина"
- **TireSetArchive** (id, original_tire_set_id, client_id, client_name, client_email, car_id, car_make, car_model, stored_at, issued_at, archived_at) — журнал выдачи шин, тот же денормализованный принцип, что у `BookingArchive`
- **OutboxEmail** (id, to, subject, body, sent_at) — заглушка почты; используется и как единственный источник идемпотентности для B6 (см. ниже)
- **StationStats** (id=1, total_revenue) — legacy-счётчик, продолжает вестись при каждой выдаче, но больше не источник истины для `/station/stats` (см. "Бизнес-правила")
- **BookingArchive** (id, original_booking_id, client_id, client_name, client_email, car_id, car_make, car_model, post_id, start_at, end_at, status, total_price, service_price, parking_surcharge, parking_wait_minutes, services_snapshot [JSON], additional_works_snapshot [JSON], created_at, archived_at) — журнал завершённых/отменённых заявок, денормализован намеренно (журнал для чтения человеком, переживает удаление самого клиента/машины/услуги); `service_price`/`parking_surcharge`/`parking_wait_minutes` (2026-09-18) — разложение `total_price` на составляющие для аудируемости, см. "Бизнес-правила"

**Поток "полное завершение / отмена" (2026-09-12):** при переходе заявки в `issued` или `cancelled` строка `Booking` убирается из активной таблицы (слот освобождается — проверки занятости и так игнорируют оба этих статуса) и переезжает в `BookingArchive` целиком, снимком на момент архивации. Выручка (`StationStats.total_revenue`) растёт только при `issued`.

## Ключевые потоки

1. **Запись клиента**: клиент выбирает услуги → backend считает свободные **моменты времени** (без привязки к посту) → клиент подтверждает время → backend сам подбирает свободный пост и создаёт `Booking` в транзакции с блокировкой строк авто и постов (защита от гонки — A4/A10).
2. **Выполнение**: `Booking` переходит `accepted → on_post` (не раньше `start_at` — см. "Бизнес-правила"), запускается автотаймер (C2, длительность = сумма длительностей услуг) → по истечении сам переводит в `awaiting_approval`/`ready` → события в SSE-канал (A6).
3. **Доп. работа**: мастер вручную (B2) создаёт `AdditionalWork` из каталога услуг → клиенту уведомление (SSE + `OutboxEmail`) → согласование только клиентом, не станцией → если сразу нет места на посту — предлагается отдельный визит (см. "Бизнес-правила").
4. **Проактивные напоминания**: B5 (ежедневно проверяет пробег/срок ТО конкретной машины, плюс сигнал "мест мало"), B6 (дважды в год, всем клиентам — не привязано к истории), B3 (за день до записи) — все через `OutboxEmail`, идемпотентность у каждого своя (см. "Бизнес-правила").
5. **Личный кабинет клиента**: сессия — не токен/куки, а `Client.id`, активный в `localStorage` браузера. Из кабинета клиент видит/редактирует свои авто и заявки, включая перенос/отмену, и может удалить сам профиль (каскадно — см. "Бизнес-правила").
6. **Автоочистка просроченных заявок**: фоновый джоб (`overdue_bookings.py`) отменяет заявки, которые пропустили `start_at` и мешают уже существующей следующей записи на том же посту (см. "Бизнес-правила").

## Бизнес-правила, принятые по ходу разработки

Пороги и определения ниже не заданы в тексте задания — решения AI (если не отмечено иначе), задокументированы здесь, а не разбросаны по коду.

- **Приём на пост не раньше `start_at`** (2026-09-14): переход `accepted → on_post` проверяет `datetime.now() >= booking.start_at`, иначе `409`. Найден пользователем как реальный баг — раньше таймер обслуживания отталкивался от момента клика, а не от расписания.
- **Occupancy у автотаймера (C2) синхронизируется только расширяя** (2026-09-14, критичный баг п.35): при запуске таймера (основной услуги или доп. работы) `service_ends_at` считается от реального "сейчас" + длительность; `end_at` (то, что проверяют EXCLUDE-ограничения A4) подтягивается к нему, если он оказался больше — никогда не сужается.
- **Доп. работа без места сейчас → отдельный визит, а не тупик** (2026-09-14–15, п.37/38): если продление occupancy для одобренной доп. работы пересеклось бы с уже существующей следующей заявкой на этом посту (проверяется проактивно, независимо от текущего статуса заявки — не только в момент реального продления), предложение остаётся `pending`, а клиенту предлагается выбрать время отдельного визита именно на эту работу (тот же виджет, что у переноса записи, B4) — решение пользователя через уточняющий вопрос.
- **Автоотмена просроченных заявок** (2026-09-15, п.39): заявка в статусе `accepted`, чей `start_at` в прошлом дольше `MIN_OVERDUE_GRACE` (2 минуты — защитный буфер, не порог для спешки), автоматически отменяется, **только если** её приём прямо сейчас пересёкся бы с другой активной заявкой на её посту. Если никому не мешает — не трогаем, сколько угодно. Джоб проверяет раз в 30 секунд.
- **B5 — пороги "пора на ТО"**: ≥6 месяцев с `last_service_date` ИЛИ ≥10 000 км с `mileage_at_last_service`. Машины без единого ТО в истории не предлагаются — нет базы для сравнения. "Мест мало" — ≤3 свободных слота на завтра для самой короткой услуги в каталоге; сигнал считается только вместе с уже имеющимся предложением по ТО, не отдельно.
- **B6 — сезонное промо про хранение шин** (2026-09-15, уточнено вопросом пользователю): это НЕ напоминание только тем, кто хранит шины — рассылка **всем** зарегистрированным клиентам, включая тех, кто никогда не пользовался услугами (цель — реклама самой услуги хранения). "Сезон" — не 4 календарных, а 2 момента в году, совпадающих с реальной сезонной переобувкой: 15 апреля (сдать зимнюю резину) и 15 октября (забрать обратно). Идемпотентность — без отдельной таблицы/флага: тема письма содержит сезон+год, повторная отправка тому же email с той же темой не происходит. Видно не только в email-заглушке, но и баннером в кабинете клиента (`GET /clients/{id}/tire-season-reminder`, читает то же самое письмо в `outbox_emails`, без отдельного состояния) — найденный пользователем пробел в первой версии. Баннер — самый верхний из всех напоминаний в кабинете и закрывается крестиком (`POST .../dismiss`, пишет `Client.tire_season_reminder_dismissed_season`) — до конца текущего сезона не возвращается, письмо в почте при этом остаётся (п.44, 2026-09-15).

  **Осознанное расширение сверх буквального требования Задания 12 (зафиксировано при аудите проекта 2026-09-17).** Буквальный текст задания: *«При наступлении сезона замены шин все клиенты **с комплектом на хранении** получают приглашение записаться»*.   **Rule-based генератор (текущая реализация, найдено пользователем на реальных данных 2026-09-15):** изначально выбирал ОДНУ самую дешёвую услугу среди широкого списка ключевых слов (масло/тормоза/фильтр/...) — на практике почти всегда сходился к одной и той же случайной дешёвой позиции ("Диагностика" за 1₽), что выглядело невзрачно и непредсказуемо.   **Открытый вопрос, зафиксированный по просьбе пользователя — это временное, заведомо грубое решение.** Настоящая диагностика должна определять реальную потребность (какая деталь реально изношена, а не "что угодно с словом ТО в названии"), а не механически перечислять всё совпавшее по имени. - **Клиент никогда не видит источник предложения доп. работы (C5, 2026-09-16)** — постоянное архитектурное правило, не разовая правка (прямая позиция пользователя): вне зависимости от того, предложил доп. работу мастер вручную или ИИ-диагностика (C4), клиентский UI (`ClientAdditionalWorks.tsx`) и клиентское письмо выглядят абсолютно одинаково. Поэтому `ai_confidence`/`ai_reason` хранятся на `AdditionalWork` только для внутреннего оверсайта станции (мастер видит в `AdditionalWorkPanel.tsx`, почему ИИ это предложил, пока человек ещё часть цикла принятия решения) и никогда не попадают ни в клиентский компонент, ни в клиентское письмо. Теперь единая функция `notify_pending_additional_works()` (`outbox_email.py`) пересчитывает ТЕКУЩИЙ полный список pending доп. работ заявки и шлёт одно нейтральное письмо с их перечислением — вызывается и из ручного предложения мастера, и после пакетной ИИ-диагностики (не по одному письму на предложение). Отдельно добавлено новое письмо "машина готова" (`notify_car_ready()`, `robot_timer.py`) — идемпотентно (проверка `was_ready` до записи статуса `ready`, так как `resolve_next_step` может быть вызван на уже готовой заявке безобидно повторно), покрывает оба пути перехода в `ready`: автотаймер и прямую ручную кнопку станции (`update_booking_status` в `bookings.py`).
- **Хранение шин привязано к реальному визиту, не к голому клику (п.47, 2026-09-16)** — пользователь лично добавил это требование в `UI_description.md` после сверки с требованиями задания. Раньше `POST /tire-sets` и `.../issue` были доступны в любой момент без всякого контекста визита. Теперь оба действия требуют, чтобы машина клиента прямо сейчас реально стояла на посту (`Booking.status == ON_POST`) по одной из двух специально заведённых, защищённых от переименования/удаления услуг каталога (`Service.protected=True`, сидируются миграцией `151f2fa88e1c` тем же приёмом, что посты в `dfe1c685b738`): **"Сезонная замена шин"** — основной сценарий сдачи (плюс явный вопрос клиенту "сдать снятые шины на хранение?", да/нет — отказ фиксируется `Booking.tire_offer_declined` через `POST /bookings/{id}/tire-storage-offer/decline`, чтобы не переспрашивать в рамках того же визита), и **"Получить/сдать шины"** — отдельный целевой визит именно за этим действием (сдача ИЛИ выдача, без вопроса). Качественный визит определяется на backend'е без изменения схемы запроса (`TireSetCreate` не получил `booking_id`) — используется уже существующий инвариант A4 "одна машина одновременно на одном посту максимум", поэтому подходящая заявка находится однозначно по `car_id` + статус + имя услуги (`app/api/tire_sets.py::_find_on_post_booking_for_service`). - **C7 — Smart Parking Management** (buisness.md, доп. требования пользователя, 2026-09-17): архитектурное решение по модели занятости поста принято ЕЩЁ на этапе A4 (см. `BUSINESS_FEATURES_REVIEW.md`, "Решение пользователя 2026-09-11") — пост занят на фиксированный интервал `[start_at, end_at)`, модель не меняется; парковка достраивается СВЕРХУ, а не переделывает A4. Все паузы на парковке используют одно и то же поле `Booking.parking_spot_id`/`parked_at` (переиспользование места между паузами, как посты между заявками), а не отдельные "до/после":
  1. **До первого приёма**: клиент из личного кабинета подтверждает, что физически привёз машину и поставил её на парковку (`POST /bookings/{id}/park`) — до этого подтверждения автоматический выезд на пост не наступит, даже если `start_at` уже прошло. Фоновый sweep (`app/services/parking.py::run_parking_sweep`, интервал 20с, тот же принцип, что и у `overdue_bookings.py`) сам принимает на пост подтвердившие приезд заявки, когда наступает время — освобождая место и накапливая в `Booking.parking_wait_minutes`, сколько машина реально прождала (см. `leave_parking`), прежде чем `parked_at` будет переиспользован под следующую паузу. Ручной путь (кнопка станции "Принять на пост") остаётся рабочим как и раньше — та же философия "ручка, которую со временем автоматизируют", что и везде в проекте; парковка для конкретной заявки в этом случае просто не использовалась.
  2. **Между раундами (ожидание решения по доп. работе)** — найдено пользователем на практике (2026-09-17), реальный пробел первой версии: место назначалось только при готовности, а между концом основной услуги и ответом клиента на предложение доп. работы (`awaiting_approval`) машина физически "нигде" — пост уже визуально свободен по расчётному интервалу, а место ожидания ещё не занято. Теперь место назначается СРАЗУ по входу в `awaiting_approval` (и через автотаймер/`resolve_next_step`, и через ручной путь в `update_booking_status` — обе точки идут через одну проверку "место ещё не назначено", как и `ready` ниже). Дальше три исхода:
     - **Клиент согласился, и на посту есть место** — машина съезжает с той же парковки обратно на пост (`leave_parking`), заявка продолжает работу.
     - **Клиент согласился, но места на посту нет** — работа переносится на отдельный визит (п.37/38); заявка остаётся на ТОМ ЖЕ месте и сразу переходит в `ready` — переназначать место не нужно, это просто продолжение той же физической стоянки.
     - **Клиент отклонил** — тот же результат: заявка на том же месте переходит в `ready`.

     **Попутно найденный и исправленный реальный баг**: перенос доп. работы на отдельный визит (`schedule_additional_work`/`schedule_additional_works_batch`) раньше помечал только САМУ работу согласованной, но никогда не проверял, осталось ли ещё что-то неотвеченное по заявке (в отличие от обычного `respond_additional_work`, где эта проверка есть) — если перенесённая работа была последним pending-предложением, заявка навсегда застревала в `awaiting_approval`, даже когда по факту уже ничего не ждёт. Теперь оба эндпоинта делают ту же проверку remaining_pending + вызов `resolve_next_step`, что и `respond_additional_work`.
  3. **После готовности**: как только заявка становится `ready` (и через автотаймер, и через ручную кнопку станции), если места ещё нет — робот сам его назначает (та же проверка "не назначено", что и для `awaiting_approval` выше — если оно уже есть с предыдущей паузы, второй раз не назначается). Клиент видит баннер в кабинете и получает письмо (C5); подтверждает, что забрал машину, тем же самым переходом в `issued` (`POST /bookings/{id}/status {issued}`) — специального отдельного эндпоинта для клиента не создавалось, поскольку в проекте нет разделения "клиент vs станция" на уровне авторизации API, оба сценария честно проходят одну и ту же бизнес-логику. Осознанное решение — не запрещать станции выдавать машину напрямую, даже если "по духу" это должен подтверждать клиент: у станции должен быть аварийный клапан на случай, когда клиент физически забрал машину, но не воспользовался кабинетом, иначе место и заявка зависли бы навечно из-за человеческого фактора.
  4. **Бесплатное время и наценка**: 2 часа суммарно на ВСЕ паузы вместе (не по 2 часа на каждую) — при выдаче (`update_booking_status`, ветка `issued`) считается `parking_wait_minutes` (сумма уже завершённых пауз) + минуты текущей паузы с последнего `parked_at`, наценка на превышение = `overdue_minutes × StationSettings.parking_overdue_rate_per_minute`, добавляется в `total_price` заявки. Ставка по умолчанию 5 ₽/мин — решение AI (задание не называет конкретную цифру), редактируется станцией через `PATCH /station/settings` (buisness.md: "по тарифу который можно менять в личном кабинете станции"). Если место так и не досталось заявке (см. п.5 ниже) — эта пауза просто не считается в простой, клиента не штрафуют за нехватку мест по вине станции.
  5. **Открытый вопрос из `BUSINESS_FEATURES_REVIEW.md`** ("что если все 6 мест заняты") — решён одинаково для ЛЮБОЙ паузы (`awaiting_approval` или `ready`): заявка остаётся без назначенного места (ничего не блокирует), а тот же `run_parking_sweep` при каждом проходе повторяет попытку для обеих категорий, пока место не найдётся.
- **Выручка считается из архива, а не из отдельного счётчика (2026-09-17/18)** — найдено сторонним ИИ-аудитом (пользователь отдельно запускал другой инструмент на проекте для проверки; здесь фиксируется его находка как принятое решение проекта, честно, а не как собственное открытие): `StationStats.total_revenue` — обычный инкрементируемый счётчик, и на практике на живой БД (ручные прогоны тестов до изоляции `db_test`) хотя бы раз реально расходился с фактическими данными archive (см. регистр багов, 2026-09-15, "уходил в минус"). `GET /station/stats` теперь считает `total_revenue` как `SUM(BookingArchive.total_price) WHERE status='issued'` — архив неизменяем и денормализован, разойтись с ним нечему; `StationStats` продолжает вестись при каждой выдаче как legacy-кэш (осознанно не удалён — не мешает, а откат к старому способу дешёвый, если понадобится). Заодно `total_price` разложен на `service_price`/`parking_surcharge`/`parking_wait_minutes`, чтобы наценку за простой на парковке можно было проверить постфактум по архивной записи, а не только по логам. **У этого стороннего аудита была своя реальная поломка** (миграция сравнивала Postgres-enum статус с `'issued'` вместо фактического `'ISSUED'`, плюс образы `backend`/`backend_test` не пересобрали после правки `Dockerfile`) — из-за неё КАЖДАЯ выдача машины на живом backend падала 500 до тех пор, пока это не нашли и не исправили (2026-09-18, см. регистр багов и `DECISIONS_LOG.md`). Сохранённые от того аудита `AGENTS.md` и `.github/workflows/ci.yml` — тоже его находки, оставлены как полезные (CI поймал бы именно эту поломку).
- **Место на парковке защищено unique-индексом, не только конвенцией кода (2026-09-18, найдено при код-ревью)** — `assign_parking_spot` и раньше не допускал гонки за счёт `SELECT ... ## Часовой пояс расчёта суток для слотов — подробности (2026-09-13)

Найден и исправлен баг: `GET /bookings/available-slots?date=` изначально трактовал переданную календарную дату как UTC-сутки. При ненулевом смещении часового пояса клиента (например, UTC-3) поздний вечер и вся ночь "сегодня" физически попадали в UTC-дату "завтра" и пропадали из выдачи — слот существовал, но не показывался под ожидаемой датой.

**Как исправлено:** backend больше не решает, что такое "сутки" — клиент (frontend) сам вычисляет момент начала суток в часовом поясе **своего устройства** (`new Date(year, month, day, 0,0,0)` — многоаргументный конструктор `Date` в JS всегда использует локальный часовой пояс) и передаёт его backend'у как точный ISO-момент со смещением. Backend просто считает окно `[date, date + 24ч)` в этих координатах — `app/services/slots.py`, `GET /bookings/available-slots`.

**Это сознательно упрощённое решение для демонстрации, согласовано с пользователем 2026-09-13.** Оно означает, что "сутки" станции сейчас равны часовому поясу устройства, на котором открыт браузер клиента — у двух клиентов из разных часовых поясов один и тот же физический слот времени попадёт под разные "дни" в их интерфейсах, и день может отличаться от того, что видит станция (если станция и клиент физически в разных поясах).

**В релизной версии** правильное поведение — привязать расчёт суток к часовому поясу **физического расположения станции**, на которую записывается клиент (а не к устройству клиента и не к UTC), поскольку время визита — это время по месту, куда клиент приедет, и оно должно выглядеть одинаково для всех, кто на него смотрит, независимо от их собственного пояса. Технически: добавить полю `Post`/станции атрибут `timezone` (IANA-имя, например `"Europe/Moscow"`), считать `day_start`/`day_end` в этом поясе (`zoneinfo.ZoneInfo`) вместо часового пояса запроса, и на фронтенде форматировать/группировать время тем же поясом (через `Intl.DateTimeFormat` с явным `timeZone`), а не локальным временем браузера.
