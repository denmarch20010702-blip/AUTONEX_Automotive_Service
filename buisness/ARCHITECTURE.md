# Архитектура — Станция техобслуживания

## Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Backend | **Python 3.12 + FastAPI** | Один из предпочтительных языков по условию задания. Async из коробки, нативная поддержка SSE/WebSocket, отличная поддержка AI-инструментами при разработке (много обучающих данных), быстрый старт без лишнего каркаса. |
| Frontend | **React + TypeScript + Vite** | Один из требуемых фреймворков. TypeScript снижает число тихих runtime-ошибок в статусной машине заявки — это прямо влияет на "доказуемость". Vite — быстрый локальный старт. |
| БД | **PostgreSQL** | Явно предпочтительный вариант по условию. Транзакции и `SELECT ... FOR UPDATE` — то, на чём держится конкурентно-безопасное бронирование слотов (A4/A10). |
| ORM/миграции | **SQLAlchemy (async) + Alembic** | Стандарт для FastAPI, явные миграции нужны, чтобы схема БД была воспроизводима при локальном разворачивании (требование "предварительные требования описаны"). |
| Realtime | **SSE (Server-Sent Events)** | Все realtime-требования задания — это push от сервера клиенту (статус заявки, занятость постов, прогресс робота), обратный канал не нужен. SSE проще WebSocket (нет двусторонней ротации соединения, тривиальный reconnect браузером из коробки) — meньше кода при том же результате. Проверено отдельно (2026-09-12): ни один из запланированных будущих шагов (B/C-грейды, включая AUTONEX C7–C13) не требует, чтобы клиент вёл непрерывный поток данных на сервер по тому же соединению — только редкие дискретные действия (клик "подтвердить", отправка оценки), которые и так идут обычным REST. WebSocket не понадобится, пока не появится принципиально другая фича вроде живого чата с мастером — сейчас такой нет ни в одном плане. |
| Шина realtime-событий | **In-process pub/sub** (`app/services/events.py`): `asyncio.Queue` на подписчика, множество подписчиков в памяти одного процесса | Тот же принцип, что и с APScheduler — один процесс, локальный быстрый запуск важнее масштабируемости, которая тут не нужна. **Известное ограничение:** это работает только в пределах одного процесса — при запуске нескольких воркеров/инстансов backend'а у каждого будет своя изолированная шина, и клиент на одном воркере не увидит событие, опубликованное другим (REST API при этом не ломается, ломается только realtime-обновление между вкладками на разных воркерах). **Путь снятия ограничения:** заменить внутреннюю реализацию `events.py` на `LISTEN`/`NOTIFY` в уже обязательном по стеку PostgreSQL (или на Redis, если он появится в проекте по другой причине) — без изменений в вызывающем коде (`create_booking`, `update_booking_status`, сам `/events`), т.к. модуль спроектирован с узким публичным интерфейсом (`publish()`/`subscribe()`), не завязанным на конкретную реализацию. |
| Фоновые задачи | **APScheduler (in-process)** | Нужны периодические проверки (проактивное ТО, сезонное напоминание по шинам, авто-выполнение задач роботом). Внешняя очередь (Celery+Redis) была бы избыточна и замедлила бы локальный запуск — требование "проект быстро разворачивается локально". |
| Email | **Заглушка** (запись в таблицу `outbox_emails` + лог в консоль) | Разрешено эмулировать внешние сервисы условием задания. |
| ИИ-модуль (C4) | **Pluggable-интерфейс**: реальный вызов LLM API, если задан ключ в `.env`; иначе — rule-based генератор с тем же контрактом | Проект должен разворачиваться локально без секретов; при этом при наличии ключа демонстрируется реальная агентная фича. |
| Авторизация | Клиент — без пароля (идентификация по email при записи). Станция/мастер — один фиксированный логин+пароль из `.env` | Условие явно разрешает "можно обойтись без входа"; полноценная ролевая система избыточна для скоупа задания. |
| Тестирование/доказуемость | **pytest** (unit + async интеграционные тесты) + отдельный скрипт `scripts/concurrency_proof.py` (параллельные запросы через `httpx.AsyncClient` / `asyncio.gather`) | Позволяет буквально показать в терминале, что гонки обрабатываются корректно — то, что просит пункт "доказуемость". |
| Контейнеризация | **docker-compose**: `db` (postgres), `backend`, `frontend` | Один `docker-compose up` — весь требуемый "быстрый локальный запуск". |

## Модель данных (основные сущности)

- **Client** (id, email, name)
- **Car** (id, client_id, make, model, mileage, last_service_date)
- **Service** (id, name, duration_minutes, price) — каталог услуг
- **Post** (id, name) — пост станции
- **Booking** (id, client_id, car_id, post_id, start_at, end_at, status, created_at) — статусы: `accepted / on_post / awaiting_approval / ready / issued / cancelled`
- **BookingService** (booking_id, service_id) — услуги, выбранные в заявке
- **AdditionalWork** (id, booking_id, description, price, proposed_by [`mechanic`/`ai`], status [`pending/approved/declined`])
- **TireSet** (id, client_id, car_id, stored_at, issued_at) — хранение шин, привязка "один комплект = один клиент+авто"
- **Robot** (id, post_id, state [`idle/working/error/done`], current_booking_id)
- **OutboxEmail** (id, to, subject, body, sent_at) — заглушка почты
- **StationStats** (id=1, total_revenue) — единственная строка-счётчик заработанных станцией денег (добавлено 2026-09-12, по прямой просьбе пользователя)
- **BookingArchive** (id, original_booking_id, client_id, client_name, client_email, car_id, car_make, car_model, post_id, start_at, end_at, status, total_price, services_snapshot [JSON], created_at, archived_at) — журнал завершённых/отменённых заявок (добавлено 2026-09-12, по прямой просьбе пользователя). Денормализовано намеренно (имя/email клиента, марка/модель авто, снимок услуг) — это журнал для чтения человеком, а не таблица для сложных отчётов, поэтому запись остаётся читаемой, даже если сам клиент/машина/услуга потом изменятся или будут удалены.

**Поток "полное завершение / отмена" (2026-09-12):** при переходе заявки в `issued` или `cancelled` строка `Booking` убирается из активной таблицы (слот освобождается — проверки занятости и так игнорируют оба этих статуса) и переезжает в `BookingArchive` целиком, снимком на момент архивации. Выручка (`StationStats.total_revenue`) растёт только при `issued` — отменённая работа деньги не приносит. Первая версия этой логики (в тот же день) вообще удаляла `issued`-заявки без следа; по обратной связи пользователя заменено на архивирование, чтобы историю можно было посмотреть при необходимости — `GET /station/archive` (опционально `?client_id=` для "моей истории" в кабинете).

## Ключевые потоки

1. **Запись клиента**: клиент выбирает услуги → backend считает свободные **моменты времени** (без привязки к посту — клиенту это не важно, слот считается доступным, если свободен хотя бы один из постов) → клиент подтверждает время → backend сам подбирает свободный пост и создаёт `Booking` в транзакции с блокировкой строк авто и постов (защита от гонки — реализовано в A4, скрипт-демонстрация — A10). Отдельно проверяется, что та же машина не занята на пересекающееся время на другом посту.
2. **Выполнение**: `Booking` переходит `accepted → on_post`, робот на посту берёт задачу в очередь, тикает прогресс (C2) → шлёт события в SSE-канал (A6/C3).
3. **Доп. работа**: робот/ИИ (C4) или мастер вручную (B2) создаёт `AdditionalWork` → клиенту уведомление (SSE + запись в `OutboxEmail`) → выполнение не продолжается, пока клиент не подтвердит/отклонит.
4. **Проактивные напоминания** (B5/B6): фоновая задача APScheduler ежедневно проверяет пробег/сроки ТО и сезон замены шин, создаёт записи в `OutboxEmail` с защитой от повторной отправки (флаг/таблица уже отправленных уведомлений).
5. **Личный кабинет клиента** (внеплановое расширение A8, 2026-09-12): сессия клиента — не токен/куки, а просто "какой `Client.id` активен на этом браузере", хранится в `localStorage` фронтенда (клиент и так без пароля — см. авторизацию выше). Несколько аккаунтов на одном браузере — несколько таких id в списке "уже известных", с переключением без повторного ввода email. Из кабинета клиент видит/редактирует свои авто и заявки, включая отмену (см. п.6).
6. **Отмена заявки** (B4, перенесено вперёд с 2026-09-12): клиент или станция переводят заявку в `cancelled` из любого нетерминального статуса. Слот освобождается автоматически — все проверки занятости (`car_is_free`, поиск свободного поста) уже исключают `cancelled`-заявки, отдельной логики "освободить" не требуется.

## Открытые вопросы к пользователю

1. **ИИ-модуль (C4)** — используем реальный вызов LLM (нужен API-ключ, будет расход) или оставляем rule-based генератор с "AI-подобным" текстом по умолчанию, а реальный вызов — опционально при наличии ключа? Архитектура уже поддерживает оба варианта через общий интерфейс — решение не блокирует старт работы.
2. **Авторизация станции** — фиксированный логин/пароль из `.env` достаточен, или нужна более серьёзная модель входа?

Это не блокирует переход к шагу A1 — оба пункта можно решить по мере реализации C4 и не влияют на схему БД или API-контур.
