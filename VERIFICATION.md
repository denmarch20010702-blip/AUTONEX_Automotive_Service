# Как самостоятельно проверить, что сделано на шагах A1/A9/A2/A2.1/A3/A4

Это доказательство того, что текущий скелет проекта (docker-compose, схема БД: `Client`, `Car`, `Service`, `Post`, `Booking`, `TireSet`, `AdditionalWork`) — рабочий и внутренне непротиворечивый: миграции не расходятся с моделями, обратимы, приложение отвечает, тесты зелёные. Плюс — сама бизнес-логика A4 (свободные слоты, конкурентно-безопасное бронирование).

## Быстрый способ — один скрипт

```bash
docker compose up -d        # если ещё не запущено
bash scripts/verify.sh
```

Работает из Git Bash, WSL или обычного терминала на Windows/macOS/Linux — внутри только `docker compose exec`/`curl`, ничего платформозависимого.

Скрипт проверяет по порядку:

1. **Все три контейнера живы** (`db`/`backend`/`frontend`) — `docker compose ps`.
2. **Backend отвечает** — `GET /health` → `{"status":"ok"}`.
3. **Frontend отвечает** — `GET /` → `200`.
4. **Миграции не ветвятся** — `alembic heads` должен показать ровно одну "head"-ревизию. Если их больше одной — значит кто-то создал две параллельные миграции от одного родителя, и это конфликт, который нужно решать `alembic merge`.
5. **Код и реальная БД не разошлись** — `alembic check` сравнивает ORM-модели с фактической структурой БД и говорит `No new upgrade operations detected`, если они совпадают. Если бы кто-то поправил модель и забыл сделать миграцию — эта команда покажет расхождение.
6. **Тесты backend** — `pytest` внутри контейнера (та же среда, что видит and CI/проверяющий).

Флаг `--full` (`bash scripts/verify.sh --full`) добавляет седьмую, разрушающую проверку — полный откат схемы БД до пустой и накат обратно (`alembic downgrade base` → `alembic upgrade head`). Это самое сильное доказательство того, что миграции консистентны: если бы `upgrade` и `downgrade` не были зеркальны друг другу (как оказалось при первой проверке — см. ниже), команда бы упала. **Стирает все данные в БД** — сейчас безопасно (реальных данных ещё нет), но как только в проекте появятся настоящие данные — этот флаг только на копии БД, не на боевой.

## Что именно нашлось и было исправлено

При первом прогоне `--full` вскрылся реальный баг: автогенерация Alembic создаёт Postgres `ENUM`-тип при `CREATE TABLE`, но не удаляет его при `DROP TABLE` в `downgrade()` — это её собственное известное ограничение (отмечено в самих файлах миграций комментарием "please adjust!", который до этой проверки никто вручную не проверил). Из-за этого повторный `upgrade` после `downgrade` падал: `type "booking_status" already exists`.

Исправлено — в `downgrade()` обеих миграций (`backend/alembic/versions/909e4725fc6d_*.py` и `c1528f5a8b01_*.py`) добавлено явное удаление ENUM-типов. После фикса цикл `upgrade → downgrade → upgrade` проходит многократно без ошибок (проверено).

## Ручная проверка API (шаг A3: Клиент/Автомобиль/Каталог услуг)

### Вариант 1 — Swagger UI в браузере (самый простой)

Открой **`http://localhost:8000/docs`**. Там интерактивная документация по всем эндпоинтам (`/clients`, `/cars`, `/catalog`) — можно раскрыть любой, нажать "Try it out", ввести данные (включая кириллицу — в браузере проблем с кодировкой нет) и выполнить запрос прямо там же, увидеть код ответа и тело. Это самый надёжный способ, рекомендую начать с него.

Альтернатива с тем же API, но в виде читаемой документации — `http://localhost:8000/redoc`.

### Вариант 2 — PowerShell

```powershell
# Создать клиента
$json = @{ email = "test@example.com"; name = "Test Client" } | ConvertTo-Json
Invoke-RestMethod -Uri "http://localhost:8000/clients" -Method Post -Body $json -ContentType "application/json"

# Список клиентов
Invoke-RestMethod -Uri "http://localhost:8000/clients"

# Получить/обновить/удалить конкретного (подставь id из ответа выше)
Invoke-RestMethod -Uri "http://localhost:8000/clients/1"
Invoke-RestMethod -Uri "http://localhost:8000/clients/1" -Method Patch -Body '{"name":"New Name"}' -ContentType "application/json"
Invoke-RestMethod -Uri "http://localhost:8000/clients/1" -Method Delete
```

**Важный нюанс, если будешь вводить кириллицу прямо в PowerShell-консоли:** сама консоль Windows PowerShell 5.1 может **отображать** кириллический ответ как нечитаемую кашу (`Ð Ñ...`) — это проверено и это проблема отображения в консоли, а не данных. Реальные данные при этом долетают до БД и хранятся в корректном UTF-8 (я это отдельно проверил через `psql`, сравнив побайтово). Если видишь такую кашу в ответе — не паникуй, проверь то же самое через Swagger UI или напрямую в БД (ниже) прежде чем считать это багом.

## Ручная проверка A4 (свободные слоты + бронирование + конкурентность)

### Через Swagger UI (`http://localhost:8000/docs`)

1. Сначала нужны данные: создай услугу через `POST /catalog` (например, `duration_minutes: 30`) — id из ответа понадобится дальше. Посты уже есть — 3 штуки, засеяны миграцией (`Пост 1/2/3`), создавать не нужно и явно указывать при записи тоже не нужно — клиенту не важно, на каком посту его обслужат, пост подбирается автоматически.
2. `GET /bookings/available-slots` с параметрами `service_ids=<id услуги>` и `date=<любая будущая дата, YYYY-MM-DD>` — в ответе только `start_at`/`end_at` (без `post_id`), слот считается доступным, если свободен хотя бы один из 3 постов. Шаг 15 минут, на все сутки (станция 24/7, рабочих часов нет).
3. Возьми `start_at` любого слота из ответа и создай заявку через `POST /bookings` — тело: `client_id`, `car_id` (создай через `/clients` и `/cars`, если ещё нет), `start_at`, `service_ids`. **`post_id` и `end_at` указывать не нужно** — пост подбирается автоматически, а конец интервала сервер сам вычисляет по сумме длительностей услуг. Ожидается `201`, `status: "accepted"` и заполненный `post_id` в ответе — какой именно пост подобрала система.
4. Повтори `GET /bookings/available-slots` с теми же параметрами — время всё ещё в списке, пока свободен хотя бы один пост (заняли только один из трёх).
5. Повтори шаг 3 ещё **два раза** с тем же `start_at`, но с новыми `client_id`/`car_id` — на третьей заявке будут заняты все 3 поста, и вот теперь то же время исчезнет из `available-slots`. Отправь `POST /bookings` на это же время в четвёртый раз — теперь ожидается `409` ("все посты заняты в это время"). Это работает не только потому, что backend сам проверяет занятость перед вставкой, а потому что дополнительно в БД стоит ограничение на уровне Postgres (`EXCLUDE USING gist`), которое не даст вставить пересекающуюся запись даже при ошибке в этой прикидочной проверке — увидеть его можно так:
   ```bash
   docker compose exec db psql -U station -d station -c "\d bookings"
   ```
   в выводе — две строки: `"no_overlapping_bookings" EXCLUDE USING gist (post_id ...)` и `"no_overlapping_car_bookings" EXCLUDE USING gist (car_id ...)`.
6. **Проверка на баг, найденный вручную при разработке:** одна и та же машина (`car_id`) не должна получить две заявки на пересекающееся время, даже на разные посты. Отправь `POST /bookings` с тем же `car_id`, что в шаге 3, и тем же `start_at` — ожидается `409` ("автомобиль уже записан на это время"), а не успешное создание на другом посту (раньше именно так один автомобиль оказывался одновременно записан на 3 поста).

### Конкурентность — через автотест (надёжнее, чем руками кликать в нескольких вкладках)

Ручное "нажать одновременно в нескольких окнах" не даёт надёжного доказательства гонки — слишком легко случайно кликнуть последовательно. Более строгое доказательство — тест, который отправляет **4 запроса на одно и то же время** по-настоящему параллельно (`asyncio.gather`), при том что свободно только 3 поста, и проверяет, что ровно три получили `201` (на три разных поста, без повторного назначения) и один — `409`.

По умолчанию `pytest` перехватывает весь вывод и показывает только `PASSED`/`FAILED`, без деталей — флаг `-s` отключает перехват, и тест печатает все 4 реальных статус-кода и тела ответов:

```bash
docker compose exec backend pytest -q -s tests/test_api_bookings.py::test_concurrent_bookings_on_same_slot_exactly_three_succeed
```

Вывод будет вида:
```
Четыре одновременных запроса на 3 поста -> статусы: [201, 201, 201, 409]
  запрос 1: 201 {'id': ..., 'post_id': 1, 'status': 'accepted', ...}
  запрос 2: 201 {'id': ..., 'post_id': 2, ...}
  запрос 3: 201 {'id': ..., 'post_id': 3, ...}
  запрос 4: 409 {'detail': 'Все посты заняты в это время'}
```

Аналогичный тест, но для бага с одной машиной на нескольких постах — 3 параллельных запроса с одним и тем же `car_id`, при том что все 3 поста свободны: ожидается ровно один `201`, остальные два — `409` (не "победили посты", а "машина уже занята"):

```bash
docker compose exec backend pytest -q -s tests/test_api_bookings.py::test_concurrent_bookings_same_car_only_one_succeeds
```

Вывод:
```
Три одновременных запроса на одну машину -> статусы: [201, 409, 409]
  запрос 1: 201 {'id': ..., 'post_id': 1, 'status': 'accepted', ...}
  запрос 2: 409 {'detail': 'Автомобиль уже записан на это время'}
  запрос 3: 409 {'detail': 'Автомобиль уже записан на это время'}
```

Можно прогнать несколько раз подряд, чтобы убедиться, что результат не случайный — он прогонялся 5 раз подряд при разработке, все 5 раз одинаково `[201, 409]`.

### Дополнительные баги, найденные при разборе логики (и исправленные)

Автотесты: `test_slots_available_right_up_to_midnight`, `test_service_longer_than_a_day_is_bookable`, `test_cannot_book_in_the_past`, `test_start_at_must_be_on_the_15_minute_grid`, `test_cannot_book_someone_elses_car`, `test_service_with_non_positive_duration_or_price_rejected`.

Вручную можно проверить владение машиной так:

1. Создай клиента A с машиной, клиента B без машины.
2. Возьми любой `start_at` из `available-slots`.
3. `POST /bookings` с `client_id` клиента **B**, но `car_id` машины клиента **A** → ожидается `403` ("автомобиль не принадлежит этому клиенту").
4. Тот же запрос с `client_id` клиента **A** (владельца) → `201`.

Проверка "нельзя в прошлое" и "только по сетке 15 минут": отправь `POST /bookings` с `start_at` в прошлом или с произвольным временем вроде `09:07:00Z` — оба случая должны вернуть `422`, а не создать заявку. Это осознанное ограничение: клиент выбирает время кликом по предложенному `available-slots`, а не вводит вручную.

## Ручная проверка БД

```bash
# Список таблиц
docker compose exec db psql -U station -d station -c "\dt"

# Содержимое конкретной таблицы
docker compose exec db psql -U station -d station -c "SELECT * FROM clients;"

# Произвольный запрос
docker compose exec db psql -U station -d station -c "SELECT c.name, a.make, a.model FROM cars a JOIN clients c ON c.id = a.client_id;"
```

Учётные данные (те же, что в `docker-compose.yml`): пользователь `station`, пароль `station`, база `station`, хост `localhost`, порт `5432` — этого достаточно, чтобы подключиться и любым GUI-клиентом (DBeaver, TablePlus, pgAdmin), если он уже стоит у тебя.

## Что это доказывает, а что — нет

**Доказывает:** инфраструктура (A1/A9) и схема БД (A2/A2.1) рабочие, согласованные между собой и с моделями в коде, миграции обратимы; CRUD для Client/Car/Service (A3) корректен; расчёт свободных слотов и конкурентно-безопасное бронирование (A4) работает под настоящей параллельной нагрузкой, а не только "в теории".

**Не доказывает** (потому что этого ещё нет в проекте): статусную машину заявки дальше "принята" (A5), realtime-обновление у двух открытых клиентов (A6), хранение шин и согласование доп. работ как процесс, не только как таблицы (B1/B2), полноценный демонстрационный скрипт-доказательство конкурентности (A10 — сейчас это покрыто автотестом, отдельного стоящего скрипта пока нет). Эти проверки появятся вместе с соответствующими шагами — см. `logs/EXECUTION_PLAN.md`.
